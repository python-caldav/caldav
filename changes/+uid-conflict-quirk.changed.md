`save.no-uid-conflict` is graded by a plain PUT, and a server refusing a duplicate UID in a way the RFC does not prescribe can be a `quirk` the library works around, with the extra keys `status` and `precondition`.  With the precondition but another status than 403 or 409 (Xandikos, Stalwart: 412) the library goes by the body, as before.  With a bare status (SOGo: 409), `save()` now raises `UidConflictError` (`UidConflictConsistencyError` with `no_overwrite` or `no_create`) where a GET finds nothing at the URL (only on a server answering 404 for a missing object, `non-existing-raises-not-found.object`); a bare 403 is not taken for a UID conflict, since a read-only calendar answers it too.  The new `save.no-uid-conflict.if-none-match` does the same for a PUT carrying `If-None-Match: *`, which some servers answer otherwise (Bedework and iCloud: a bare 412).
