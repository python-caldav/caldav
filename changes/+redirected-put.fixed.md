A PUT that the server redirected with a 302 was followed by niquests/requests as a GET without the body, so the data was lost without an error; with httpx `save()` even reported success and moved the object's `url` to the Location.  Zimbra does this with an object saved under a name other than `<uid>.ics`: it answers 302 to `<uid>.ics` and stores nothing.  A request other than GET and HEAD answered with 301, 302, 307 or 308 is now repeated at the Location with its method and body, if that is on the same host, port and scheme (or an upgrade from http to https), and `save()` and calendar creation move the `url` there.  A 303 to a PUT is taken as success, with the object at the Location.  A redirect to another host or port, followed before by the HTTP library for methods other than PUT, is no longer followed; `save()` raises `PutError` on it instead of reporting success.
